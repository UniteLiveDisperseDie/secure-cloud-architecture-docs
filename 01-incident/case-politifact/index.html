    PolitiFact

    1. 개요

    1.1 사고 배경

    2017년은 비트코인을 비롯한 암호화폐 시장이 급격한 가격 상승을 보이며 전 세계적인 관심을 끌던 시기입니다. 이 흐름에 편승해 타인의 컴퓨팅 자원을 무단으로 채굴에 동원하는 크립토재킹이 새로운 사이버 위협으로 부상하였습니다. CoinHive는 2017년 9월 등장한 자바스크립트 기반 채굴 스크립트로, 웹사이트에 삽입하면 방문자의 브라우저를 통해 모네로(Monero) 암호화폐를 채굴할 수 있습니다. 일부 웹사이트는 광고 수익을 대체하는 수단으로 이를 정상적으로 활용하기도 하였으나, 방문자의 동의 없이 악의적으로 삽입하는 사례가 같은 시기 Showtime, The Pirate Bay 등 대형 사이트에서도 잇달아 발견되면서 크립토재킹은 주요 보안 위협으로 자리잡기 시작하였습니다.

    1.2 사고 요약

    미국의 대표적인 팩트체킹 언론사인 PolitiFact의 공식 웹사이트가 2017년 10월 13일 공격자에 의해 침해되었습니다. 공격자는 사이트에 CoinHive 스크립트를 무단 삽입하여 방문자 모르게 그들의 컴퓨터 자원을 모네로 채굴에 동원하였습니다. 특히 이번 사고에서는 CoinHive 인스턴스를 수십 개 동시에 실행하는 방식을 사용해 방문자 컴퓨터의 CPU를 즉시 100%까지 끌어올렸습니다.

    주요 사고 현황은 다음과 같습니다.

    • 최초 발견: 보안 연구자 Troy Mursch가 사이트 방문 중 CPU 과부하 현상을 감지
    • 피해 대상: PolitiFact 웹사이트 방문자 전원
    • 피해 유형: 방문자 동의 없는 컴퓨팅 자원 무단 탈취, 시스템 성능 저하
    • 데이터 유출: 없음
    • 조치 완료: 당일 오후 4시경 악성 스크립트 제거 완료

    2. 공격 분석

    2.1 공격 흐름 (Attack Flow)

    이번 공격은 서버나 데이터베이스를 직접 침해하는 전통적인 방식과 달리, 웹사이트를 매개체로 삼아 불특정 다수의 방문자 컴퓨터를 공격 인프라로 전환시키는 구조입니다. 공격의 최종 목적은 데이터 탈취가 아닌 채굴 수익 확보로, 피해자는 피해 사실을 인지하기 어렵다는 특징이 있습니다.

    전체 공격 흐름을 도식화하면 아래와 같습니다.

    [제3자 광고 제공업체 또는 CMS 취약점 침해]
               |
               v
  [PolitiFact 웹사이트에 CoinHive 스크립트 삽입]
               |
               v
       [방문자가 사이트 접속]
               |
               v
  [브라우저에서 CoinHive 자바스크립트 자동 실행]
               |
               v
  [방문자 CPU 자원으로 모네로 채굴 수행]
               |
               v
     [채굴 수익이 공격자에게 귀속]

    2.2 단계별 공격 프로세스

    1단계: 최초 침입 (Initial Access)

    PolitiFact 측은 침입 경로로 제3자 광고 제공업체(Ad Provider)를 통한 경로를 유력하게 지목하였습니다. 이는 광고 스크립트가 웹사이트에 동적으로 삽입되는 구조적 특성을 악용한 것으로, 광고 공급망 어딘가에서 악성 스크립트가 주입되었을 가능성이 높습니다. 웹사이트 CMS(콘텐츠 관리 시스템)의 취약점이나 관리자 계정 침해를 통한 직접 삽입 가능성도 배제할 수 없습니다.

    2단계: 악성 스크립트 삽입 (Malicious Script Injection)

    공격자는 CoinHive 자바스크립트 코드를 PolitiFact 웹페이지에 삽입하였습니다. 일반적인 CoinHive 악용 사례와 달리, 이번 사고에서는 다음과 같은 특이점이 관찰되었습니다.

    • CoinHive 인스턴스를 수십 개 동시에 구동하도록 설정
    • 방문자의 CPU 자원을 최대한 빠르게 100%까지 소진시키는 방식을 채택
    • 방문자에게 별도의 동의나 고지 없이 채굴이 즉시 시작되도록 구성

    3단계: 방문자 브라우저를 통한 채굴 실행 (Execution)

    방문자가 PolitiFact 웹사이트에 접속하는 순간, 브라우저가 페이지를 렌더링하는 과정에서 삽입된 CoinHive 스크립트가 자동으로 실행됩니다. 별도의 파일 다운로드나 설치 과정 없이 브라우저 내에서 모든 채굴 연산이 수행되므로, 방문자는 의심하기 어렵습니다. 채굴되는 암호화폐는 모네로(Monero)로, 비트코인 대비 거래 추적이 어렵다는 특성 때문에 이러한 불법 채굴에 자주 활용됩니다.

    4단계: 수익 귀속 (Impact)

    채굴된 모네로는 전량 공격자의 지갑 주소로 귀속됩니다. 방문자 수가 많은 유명 언론사 사이트를 표적으로 삼았기 때문에, 다수의 고성능 컴퓨터를 동시에 채굴에 동원하는 효과를 노린 것으로 분석됩니다.

    3. 대응 방안

    3.1 즉각 대응 절차

    크립토재킹이 탐지되거나 의심되는 경우 아래 순서로 즉각 대응을 수행하여야 합니다.

    [1] 악성 스크립트 식별 및 제거

    • 웹사이트 소스코드 전체를 점검하여 CoinHive 또는 유사 채굴 스크립트 삽입 여부를 확인합니다.
    • 외부에서 로드되는 서드파티 스크립트 목록을 전수 조회하고 불명확한 출처의 스크립트를 즉시 차단합니다.
    • 악성 스크립트 확인 즉시 해당 코드를 삭제하고 페이지를 재배포합니다.

    [2] 클라우드 인프라 기반 즉각 격리

    웹사이트가 AWS, GCP, Azure 등 클라우드 환경에서 운영 중인 경우, 아래 조치를 병행합니다.

    • AWS WAF(Web Application Firewall) 규칙을 즉시 갱신하여 알려진 CoinHive 도메인(coinhive.com, coin-hive.com 등) 및 채굴 풀 서버로의 아웃바운드 트래픽을 차단합니다.
    • AWS CloudFront 배포 설정에서 의심 스크립트가 캐시되어 계속 서비스되지 않도록 캐시를 즉시 무효화(Invalidation)합니다.
    • 보안 그룹(Security Group) 또는 네트워크 ACL을 수정하여 웹 서버 인스턴스의 불필요한 아웃바운드 포트를 임시 차단합니다.

    [3] 광고 제공업체 및 공급망 점검

    • 연동된 제3자 광고 네트워크 및 CDN을 통해 로드되는 모든 외부 자원의 무결성을 점검합니다.
    • 해당 광고 제공업체에 즉시 침해 사실을 통보하고 악성 광고 스크립트 배포 중단을 요청합니다.

    [4] 관리자 계정 및 CMS 보안 점검

    • 웹사이트 CMS 관리자 계정의 비밀번호를 즉시 변경하고 최근 로그인 이력을 조회합니다.
    • AWS CloudTrail 로그를 조회하여 인프라 설정 변경 이력 및 비정상 API 호출 여부를 확인합니다.
    • CMS 및 플러그인의 최신 보안 패치 적용 여부를 점검합니다.

    [5] 방문자 및 이해관계자 공지

    • 사고 사실과 조치 현황을 투명하게 공지하여 방문자의 신뢰를 유지합니다.
    • 방문자에게 JavaScript 비활성화 또는 광고 차단기 사용을 임시 방편으로 안내합니다.

    3.2 사후 조치 및 재발 방지

    콘텐츠 보안 정책(CSP) 적용

    재발 방지의 가장 핵심적인 기술적 조치는 CSP(Content Security Policy) 헤더를 적용하는 것입니다. CSP를 통해 웹사이트에서 실행 가능한 스크립트의 출처를 화이트리스트 방식으로 명시적으로 제한하면, 승인되지 않은 외부 스크립트가 삽입되더라도 브라우저 단에서 실행 자체를 차단할 수 있습니다. AWS CloudFront를 사용하는 경우 응답 헤더 정책(Response Headers Policy)을 통해 CSP를 중앙에서 일괄 적용할 수 있습니다.

    클라우드 인프라 기반 탐지 체계 구축

    크립토재킹은 방문자 측에서 발생하는 특성상 서버 단에서 직접 탐지하기 어렵습니다. 그러나 클라우드 인프라 레이어에서는 다음과 같은 간접 탐지 수단을 활용할 수 있습니다.

    • AWS WAF 로그 분석: 채굴 풀(Mining Pool) 관련 도메인으로의 요청 패턴이나 CoinHive 관련 스크립트 URL 요청을 WAF 로그에서 탐지하는 규칙을 설정합니다. AWS Managed Rules에 포함된 악성 IP 목록과 연동하면 알려진 채굴 인프라로의 접근을 자동 차단할 수 있습니다.
    • Amazon CloudWatch 이상 탐지: EC2 웹 서버 인스턴스의 CPU 사용률, 네트워크 아웃바운드 트래픽을 CloudWatch로 상시 모니터링하고, 임계치 초과 시 알람을 발송하도록 설정합니다. 채굴 스크립트가 서버 측에도 부하를 유발하는 경우 이 방법으로 이상 징후를 조기에 포착할 수 있습니다.
    • AWS GuardDuty 활성화: GuardDuty는 DNS 쿼리 로그 및 VPC 플로우 로그를 분석하여 알려진 암호화폐 채굴 도메인 및 채굴 풀 서버로의 통신을 탐지합니다. CryptoCurrency:EC2/BitcoinTool.B 등의 GuardDuty 위협 인텔리전스 시그니처가 이에 해당하며, 탐지 즉시 SNS 알림과 연동하여 자동 대응 워크플로우를 구성할 수 있습니다.
    • AWS CloudTrail 이상 탐지: 웹 서버 배포 환경의 설정 파일이나 S3에 호스팅된 정적 자원이 변경된 경우 CloudTrail 이벤트로 기록됩니다. CloudTrail Insights를 활성화하면 비정상적인 API 호출 패턴을 자동으로 탐지하고 경보를 발생시킬 수 있습니다.
    • Amazon Macie 활용: S3 버킷에 저장된 웹 자원 파일에 비정상적인 스크립트 코드가 포함되어 있는지 Macie의 민감 데이터 탐지 기능을 확장하여 모니터링하는 방안을 검토합니다.

    서브리소스 무결성 검증(SRI) 도입

    • 외부 CDN이나 광고 네트워크를 통해 로드하는 모든 스크립트에 SRI(Subresource Integrity) 해시를 적용합니다.
    • 스크립트 파일이 변조된 경우 브라우저가 자동으로 로드를 거부하도록 설정합니다.
    • AWS CloudFront 함수(CloudFront Functions) 또는 Lambda@Edge를 활용하면 엣지 레이어에서 SRI 헤더를 동적으로 삽입하거나 외부 스크립트 응답의 해시를 검증하는 로직을 구현할 수 있습니다.

    제3자 광고 공급망 보안 강화

    이번 사고의 가능성 높은 침입 경로가 광고 제공업체였다는 점에서, 광고 공급망 보안 관리는 매우 중요합니다.

    • 연동하는 광고 네트워크의 보안 정책 및 사고 이력을 정기적으로 검토합니다.
    • 광고 스크립트가 로드하는 추가 자원의 도메인을 AWS WAF 또는 Route 53 Resolver DNS Firewall을 통해 주기적으로 모니터링하고 허용 목록 외의 도메인을 차단합니다.
    • 불필요한 광고 제공업체 연동을 최소화하여 공격 노출 면적을 줄입니다.

    실시간 모니터링 체계 구축

    • 웹사이트 방문자의 비정상적인 CPU 사용량을 감지하는 실제 사용자 모니터링(RUM, Real User Monitoring) 솔루션을 도입합니다.
    • AWS CloudWatch Synthetics를 활용하여 주기적으로 자사 웹사이트를 자동 방문하고, 페이지 로드 시 비정상적인 스크립트가 실행되는지 카나리(Canary) 테스트를 통해 탐지합니다.
    • Amazon EventBridge와 Lambda를 연동하여 GuardDuty 또는 WAF에서 이상 탐지 이벤트 발생 시 자동으로 해당 EC2 인스턴스를 격리하거나 CloudFront 배포를 비활성화하는 자동 대응 워크플로우를 구성합니다.

    CMS 및 계정 보안 강화

    • CMS 관리자 계정에 다단계 인증(MFA)을 필수 적용합니다.
