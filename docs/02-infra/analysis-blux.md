이 자료는 SaaS 아키텍처 패턴과 이를 EKS로 구현한 사례인데, 관련 개념에 대해 살펴보기 좋은 것 같습니다.

![](https://velog.velcdn.com/images/hvvup/post/090636f2-147a-4d98-97d7-d360bff47de0/image.png)

SaaS는 **Software as a Service**의 약자로, 하나의 소프트웨어를 여러 고객에게 제공할 때 격리된 테넌트 구조를 통해 제공합니다. 그림에서도 나와있듯이, 각 테넌트에는 이 소프트웨어의 고객이 자리하게 됩니다. 이때 pool, silo 등의 방식으로 어떤 리소스를 얼마나 분리할 것인지에 따라 나뉘게 됩니다. 이 방식은 SaaS를 제공하는 업체가 즉시 고객에게 서비스할 수 있고, 인프라를 일관되게 유지 및 관리할 수 있습니다.


# 1. 개요

## 1.1 인프라 구성 요약

주요 구성 요소는 다음과 같습니다.

- 컴퓨팅: Amazon EKS (Kubernetes 클러스터)
- 네트워크: AWS ALB (Application Load Balancer), Amazon Route 53
- 스토리지: Amazon DynamoDB (행동 데이터 및 추천 로그), Amazon S3 (모델 아티팩트), Amazon RDS (테넌트 인증 데이터)
- ML 파이프라인: Airflow, MLflow
- 관측 가능성: EFK 스택 (Elasticsearch, Fluentd, Kibana), Prometheus, Grafana
- CI/CD: Jenkins, ArgoCD

Blux의 모든 워크로드는 Amazon EKS 클러스터 위에서 동작합니다. HPA가 Pod를, Karpenter가 Node를 자동으로 스케일링하여 안정성을 유지하며, EFK 스택으로 로깅, Prometheus·Grafana로 모니터링, Jenkins와 ArgoCD로 CI/CD를 운영합니다.

테넌트는 SDK를 통해 두 API를 호출하며, 모든 요청은 ALB를 통해 EKS 파드로 전달됩니다.

- **Collector API**: 유저의 행동 데이터를 수집해 DynamoDB에 저장합니다.
- **ML API**: 학습된 모델을 기반으로 실시간 추천을 제공합니다.

**추천 흐름**
ML API 호출 시, 인증 후 테넌트 전용 Recommender 워크로드로 요청이 전달됩니다. Recommender는 DynamoDB에서 유저의 최신 행동 데이터를, S3에서 전용 추천 모델을 읽어 실시간 추천을 응답합니다. 추천 결과 역시 DynamoDB에 기록됩니다.

> Collector와 ML 워크로드는 모든 테넌트가 공유하지만, Recommender 워크로드는 테넌트별로 독립 운영됩니다.

**모델 학습 및 배포**
추천 모델은 Airflow/MLflow를 활용해 주기적으로 학습 및 배포됩니다.

## 1.2 분석 범위 및 목적

Amazon EKS 기반 멀티테넌트 환경에서는 단순한 기능 구현을 넘어, 테넌트 간 데이터 격리와 클러스터 전반의 보안이 핵심 과제입니다.

## 2.2 구성 요소별 역할

- Collector 워크로드
모든 테넌트가 공유하는 워크로드로, 유저의 행동 데이터를 수신하여 DynamoDB에 저장하는 역할을 담당합니다. 인증은 RDS를 조회하는 방식으로 이루어지며, 인증 통과 후 데이터를 적재합니다.

- ML 워크로드
모든 테넌트가 공유하는 워크로드로, 추천 요청을 수신한 후 인증을 거쳐 해당 테넌트의 Recommender 워크로드로 요청을 전달합니다.

- Recommender 워크로드
테넌트별로 독립적으로 존재하는 워크로드입니다. DynamoDB에서 유저의 최신 행동 데이터를 읽고, S3에서 해당 테넌트 전용의 추천 모델을 로드하여 실시간 추천을 응답합니다. 추천 결과는 다시 DynamoDB에 기록됩니다.

- Airflow / MLflow
ML 모델의 학습 스케줄링(Airflow)과 실험 추적 및 모델 관리(MLflow)를 담당합니다. 학습 완료된 모델 아티팩트는 S3에 저장됩니다.

- ArgoCD / Jenkins
Jenkins가 CI(빌드, 테스트, 이미지 생성)를 담당하고, ArgoCD가 GitOps 방식으로 CD(배포)를 담당합니다.

# 3. 보안 관점 분석

## 3.1 현재 보안 구성 현황

### 3.1.1 테넌트 인증 (Authenticate Tenants)
다이어그램에서 명시적으로 표현된 보안 요소입니다. 모든 API 요청은 RDS에 저장된 데이터를 기반으로 인증을 수행하며 인증 실패 시 요청이 거부됩니다. 인증은 애플리케이션 레이어(워크로드 내부)에서 처리됩니다.

일반적인 구현 패턴은 다음과 같습니다.

```
테넌트 SDK → Authorization: Bearer {api_key} 헤더 포함 요청
                │
                ▼
        워크로드 파드에서 RDS 조회
                │
         ┌──────┴──────┐
       인증 성공      인증 실패
         │                │
      처리 계속        요청 거부
```

인증이 애플리케이션 레이어에서 처리된다는 것은 인증 로직이 인프라가 아닌 코드 안에 구현되어 있다는 뜻입니다. 이는 유연한 인증 정책(요금제별 접근 제어, 테넌트별 기능 플래그 등)을 구현하기 용이하다는 장점이 있습니다.

그러나 동시에 인증 로직의 책임이 전적으로 애플리케이션 코드에 달려 있음을 의미하기도 합니다. 서비스 메시나 API Gateway 레벨에서 인증을 처리하는 방식과 비교했을 때, 애플리케이션 레이어 인증은 코드 버그나 라이브러리 취약점에 더 직접적으로 노출됩니다.

### 3.1.2 테넌트별 Recommender 워크로드 격리
Recommender 워크로드는 테넌트마다 별도로 존재하여, 애플리케이션 레벨에서 테넌트 간 데이터 격리를 보장합니다. Tenant A의 Recommender 파드는 Tenant A의 모델 아티팩트와 행동 데이터만 접근하도록 설계되어 있습니다.

격리가 제공하는 보안 효과는 다음과 같습니다.

1. 데이터 접근 경계 명확화
각 Recommender 파드는 자신이 담당하는 테넌트의 데이터만 처리하도록 설계되어 있습니다. ML 워크로드가 tenant_id를 기반으로 해당 테넌트의 Recommender 파드로만 요청을 전달하기 때문에, 애플리케이션 로직 레벨에서 테넌트 간 데이터 혼재가 발생하기 어려운 구조입니다.

2. 장애 격리(Fault Isolation)
특정 테넌트의 Recommender 파드에 문제가 발생하더라도 다른 테넌트의 파드는 영향을 받지 않습니다. 이는 가용성 측면뿐 아니라 보안 측면에서도 중요합니다. 예를 들어 특정 테넌트의 파드가 비정상적인 동작을 보이거나 침해되더라도 그 영향이 다른 테넌트로 전파되는 것을 제한합니다.

3. 감사 및 추적 용이성
파드가 테넌트별로 분리되어 있으므로, 특정 테넌트와 관련된 이벤트 로그를 파드 단위로 분리하여 수집하고 분석하기가 수월합니다.

다만 현재의 격리는 애플리케이션 레이어에서만 이루어지고 있습니다. 즉, 테넌트 격리의 보장이 전적으로 ML 워크로드의 라우팅 로직이 올바르게 동작한다는 전제에 의존합니다. 코드 오류 또는 의도적인 조작 시 격리가 깨질 수 있으므로 네트워크 레이어(Network Policy)나 AWS 권한 레이어(IRSA)를 통한 다계층 보안 조치가 필요합니다.

### 3.1.3 로깅 및 모니터링 인프라
EFK 스택을 통해 클러스터 전반의 로그가 중앙화되며 Prometheus와 Grafana를 통해 메트릭 기반 모니터링이 가능합니다. 이는 보안 이벤트 탐지 및 사후 분석의 기반이 됩니다.

로그가 각 파드에 분산 저장되는 경우 파드가 삭제되거나 Node가 교체되면 로그도 함께 사라집니다. 보안 사고가 발생했을 때 공격자가 파드를 재시작하거나 삭제하는 것만으로 증거를 인멸할 수 있습니다. 중앙화된 로깅을 통해 파드의 수명과 무관하게 로그를 보관 및 저장하여 사후 분석에 사용할 수 있습니다.


## 3.2 식별된 취약점

### 3.2.1 인증 레이어의 단일 지점 구성
현재 Blux 아키텍처에서 테넌트 인증은 애플리케이션 레이어, 즉 Collector/ML 워크로드 내부에서만 이루어집니다. 요청이 ALB를 통과하고 파드에 도달한 뒤에야 비로소 RDS를 조회하여 인증이 수행되는 구조입니다.

1. 인증 로직의 버그가 전체 테넌트에 영향
Collector 및 ML 워크로드가 공유 워크로드이므로, 인증 로직의 버그 또는 우회 시 모든 테넌트에 영향을 줄 수 있습니다.

2. 클러스터 내부에서는 인증 없이 파드 간 통신이 가능
ALB 레벨 또는 서비스 메시 레벨의 인증 레이어가 없어, 내부 클러스터 네트워크에서는 인증 없이 파드 간 통신이 가능할 수 있습니다.

> **서비스 메시 레벨 인증 (mTLS)**
서비스 메시(Service Mesh)는 클러스터 내 파드 간 통신을 제어/관찰/보안하는 인프라 레이어입니다.
서비스 메시가 없는 환경에서는 파드 간 통신이 기본적으로 평문(HTTP)으로 이루어지며 통신하는 상대방이 신뢰할 수 있는 파드인지 검증하는 수단이 없습니다.
서비스 메시를 도입하면 각 파드 옆에 사이드카 프록시(Envoy 등) 가 자동으로 배포되어 모든 네트워크 트래픽이 이 프록시를 통해 흐릅니다.

이때 서비스 메시는 mTLS(mutual TLS) 를 통해 양방향 인증을 수행합니다. 일반적인 HTTPS(TLS)는 클라이언트가 서버를 인증하는 단방향 인증인 반면, mTLS는 서버도 클라이언트의 인증서를 확인하는 양방향 인증입니다.

서비스 메시는 이 인증서를 자동으로 발급하고 갱신하며, 정책으로 특정 서비스만 다른 서비스에 접근할 수 있도록 제어할 수 있습니다. Blux 아키텍처에서는 ML 파드만 Recommender 파드에 접근 가능하도록 강제할 수 있습니다.

3. RDS 장애가 인증 불가 상태로 이어짐
RDS 직접 조회 방식은 매 요청마다 DB 레이턴시와 부하를 발생시키며, RDS 장애 시 인증 자체가 불가능해지는 SPOF 문제가 있습니다.

> **SPOF (Single Point of Failure)**
SPOF란 시스템에서 해당 구성 요소 하나가 장애를 일으키면 전체 시스템이 멈추는 지점을 의미합니다.
SPOF는 가용성 문제이기도 하지만, 보안 관점에서도 중요합니다. 인증 시스템이 멈추면 서비스를 완전히 차단하거나(안전하지만 가용성 손실), 인증을 우회하거나(가용하지만 보안 위협) 둘 중 하나를 선택해야 하는 상황에 놓이기 때문입니다.

### 3.2.2 파드 수준의 AWS 리소스 접근 제어 불명확
Blux 아키텍처에서 Recommender 파드는 DynamoDB에서 유저 행동 데이터를 읽고, S3에서 모델 아티팩트를 로드합니다. 이때 DynamoDB 및 S3 접근 제어에 대해서는 명시되어있지 않습니다. 파드 수준의 AWS IAM 접근 제어(IRSA)가 적용되지 않은 경우, 다음과 같은 위험이 존재합니다.

- Node IAM Role에 과도한 권한이 부여되면, 해당 Node의 모든 파드가 동일한 권한으로 AWS 리소스에 접근 가능합니다.
- Tenant A의 Recommender 파드가 Tenant B의 S3 모델 아티팩트에 접근할 수 있습니다.

> 파드 수준의 접근 제어: **IRSA (IAM Roles for Service Accounts)**
IRSA는 Kubernetes Service Account와 AWS IAM Role을 연결하여, 파드 단위로 독립적인 AWS 접근 권한을 부여하는 메커니즘입니다.
IRSA는 Kubernetes Service Account와 AWS IAM Role을 OIDC(OpenID Connect)를 통해 연결합니다. 파드가 AWS SDK로 요청을 보낼 때, Service Account 토큰을 제시하면 AWS STS(Security Token Service)가 이를 검증하고 임시 자격증명을 발급합니다.

### 3.2.3 파드 간 네트워크 통신 제어 부재
기본적으로 Kubernetes 클러스터 내 모든 파드는 서로 자유롭게 통신 가능합니다. Network Policy가 적용되지 않은 경우 다음과 같은 위험이 존재합니다.

- 악의적인 코드가 실행된 파드에서 다른 테넌트의 Recommender 파드로 직접 요청 가능합니다.
- Airflow, MLflow, ArgoCD 등 관리 도구 파드에서 프로덕션 워크로드로의 접근을 제한할 수 없습니다.

## 3.3 개선 권고사항

인증 단일 지점 문제는 인증 레이어를 다계층으로 분산함으로써 해결합니다.

**Redis 캐싱으로 RDS SPOF 완화**
RDS를 직접 매번 조회하는 대신, Redis를 캐싱 레이어로 앞에 두어 RDS 의존성을 줄입니다. Redis가 인메모리로 인증 데이터를 보유하고 있기 때문에 RDS가 일시적으로 장애를 일으키더라도 캐시 TTL 내의 요청은 정상 처리됩니다. RDS의 부하 또한 크게 줄어드는 부가 효과도 있습니다.

**서비스 메시(Istio) 도입으로 클러스터 내부 인증 추가**
Istio를 도입하면 클러스터 내 모든 파드 간 통신에 mTLS를 강제할 수 있으며 애플리케이션 코드 변경 없이 서비스 레벨 인가 정책을 적용할 수 있습니다.

테넌트별로 Service Account와 IAM Role을 분리하여 파드 수준의 최소 권한 부여를 고려해볼 수 있습니다.
